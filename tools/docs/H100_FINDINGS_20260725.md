# H100 session, 25/07/2026 — findings

Pod: RunPod H100 SXM 80GB HBM3, driver 580.126.09, image `vllm/vllm-openai:v0.25.1`,
torch 2.11.0+cu130. About 1.5 hours, roughly $6. Logs in `results_h_*`,
`results_ngram_*`, `int4_micro*.log`, `marlin.log`, `rig_tune.log`.

Purpose: replace the RTX 4090 rig, which had mispredicted every kernel-level
experiment (fp8 KV, BitsAndBytes W4), and then use a trustworthy rig to settle
the INT4 and speculative-decoding questions.

---

## 1. The rig: what it took to model a MiG slice

The BTC target is a MiG 1g.18gb partition of an H200 — about **16 of 132 SMs**
and about **1/8 of memory bandwidth (~600 GB/s)**. The old rig capped CPU cores
and VRAM only, leaving 128 Ada SMs and full bandwidth.

**Step 1, CUDA MPS SM cap.** `nvidia-cuda-mps-control -d` plus
`CUDA_MPS_ACTIVE_THREAD_PERCENTAGE=12`. Verified, not assumed:

| | uncapped | capped 12% |
|---|---|---|
| SMs visible to torch | 132 | **14** |
| bf16 GEMM | 801 TFLOPS | 98 (8.2× ✓) |
| bulk 512MB read | 2936 GB/s | 871 |
| batch-1 GEMV 8192×2048 | 10.6 µs @ 3171 GB/s | 33.2 µs @ 1011 GB/s |

**Step 2, the acceptance test — which the bare cap FAILED.** H0 (fp8, =submit_020)
and H1 (bf16, =submit_018) both returned TPOT p50 **3.17ms**. The portal pays
**1.74ms** and about 13 points for exactly that difference. Ratio 1.00 against a
required 1.43.

Cause: MPS partitions SMs but **not the memory subsystem**, so 14 SMs still drew
the full 3.35 TB/s. The bottleneck inverted — the pod became SM starved where the
slice is bandwidth starved. This is the opposite bias to the 4090, and it means
the pod *under*-values byte-saving rather than over-valuing it.

**Step 3, a bandwidth hog.** A second MPS client streaming large buffers
(`tools/runpod/bw_hog.py`) soaks the surplus. **Tune by the compute:bandwidth
ratio, not absolute GB/s** — the hog steals SMs too, so chasing 600 GB/s alone
just over-starves compute:

| hog | TFLOPS | GB/s | TFLOPS per GB/s |
|---|---|---|---|
| none | 98.6 | 868 | 0.114 |
| **60% / 4GB** | 54.2 | 263 | **0.206** |
| 80% / 8GB | 42.1 | 212 | 0.199 |
| 88% / 12GB | 34.9 | 203 | 0.172 |
| MiG 1g.18gb (target) | ~115 | ~600 | **≈0.19** |

**Result: `SM_PCT=12` + `HOG_PCT=60 HOG_GB=4` gives a uniform ~1.9–2× scale model
of the slice** (TPOT 7.80ms vs portal 4.07 = 1.92×; shared-mode TTFT 83 vs 42 =
1.98×). Divide local latencies by ~2. Reusable for any future idea.

Caveat kept on the record: the end-to-end bf16/fp8 TPOT ratio was never
re-measured with the hog running. Only the GEMM-level ratio is known, and it
reached 1.29 against the portal's 1.43 — better, still short.

## 2. The cost model is closed (1% agreement with the portal)

Weight shapes read from the safetensors headers, not config.json — the
config-derived enumeration was wrong, claiming 1.439B linear params for a 1.17B
model:

| tensor | out × in | count | params |
|---|---|---|---|
| `w1`, `w3` (MLP gate/up) | 8192 × 2048 | 16 each | 268M each |
| `w2` (MLP down) | 2048 × 8192 | 16 | 268M |
| `in_proj` (ShortConv) | 6144 × 2048 | 10 | 126M |
| `out_proj` (attn o + conv out) | 2048 × 2048 | 16 | 67M |
| `q_proj` | 2048 × 2048 | 6 | 25M |
| `k_proj`, `v_proj` | 512 × 2048 | 6 each | 6M each |

Linears total **1.036B** (MLP is 78%); the tied embedding/lm_head is **0.134B**
and stays BF16 under `--quantization=fp8`.

At 600 GB/s those bytes predict a bf16→fp8 saving of **1.72ms**. The portal
measured **1.74ms** (submit_018 minus submit_020). **The linear layers run at
exactly memory speed on the slice, with no residual kernel tax**, which pins the
budget:

```
TPOT 4.07ms = 1.73ms fp8 linears + 0.45ms bf16 embedding + ~1.9ms everything else
```

The ~1.9ms is roughly 150 small kernels on 16 SMs — attention, ShortConv state
ops, 32 RMSNorms, RoPE, sampling.

## 3. INT4 — closed, two independent kills

`tools/runpod/marlin_bench.py`, real shapes, calibration-free symmetric
groupwise RTN at group 128 (the only legal path: BTC forbids offline or
prepacked target weights).

**W4A8 is hardware-blocked.** `Marlin W4A8-FP8 only support SM89 or SM12x
device`. SM89 is Ada, SM12x is Blackwell; the contest runs on **SM90**. vLLM's
own message adds "It is slower than Marlin W4A16 on other devices."

**W4A16 is 1.63× slower than fp8**, at every batch from 1 to 8:

| batch | fp8 | W4A16 | fp8/W4A16 |
|---|---|---|---|
| 1 | 3.61ms | 5.89ms | **0.61** |
| 2 | 3.62 | 5.87 | 0.62 |
| 4 | 3.62 | 5.97 | 0.61 |
| 8 | 3.68 | 5.97 | 0.62 |

Marlin reached only 88 GB/s against fp8's 288 GB/s on the same rig — compute
bound, not bandwidth bound. At m=1 it must dequantize int4→fp16 and use fp16
tensor cores, while fp8 W8A8 uses native Hopper fp8 with **zero dequant**;
Marlin is tuned for m≈16–64. Scaled to the slice: W4A16 ≈2.8ms vs fp8 1.73ms.

Since the rig handicaps SM-hungry kernels, a 0.61 ratio **cannot** flip on the
portal. This confirms the law first stated after submit_021: *quantization only
wins where there is no dequant/quant tax.* The projected prize was ERS 69.7
(linears) or 72.6 (including the embedding) — real, but unreachable with this
kernel.

## 4. Draft-model speculative decoding — architecturally blocked

`vllm/v1/spec_decode/llm_base_proposer.py::validate_same_kv_cache_group`, still
present and **unconditional** on main at commit `0ba2aa3` (25/07):

```python
assert len({kv_cache_groups[n] for n in self._draft_attn_layer_names}) == 1, \
    "All drafting layers should belong to the same kv cache group"
```

Groups come from the **target's** `kv_cache_config`. A hybrid target splits into
several groups (6 full-attention vs 10 ShortConv, different page sizes), so the
draft's layers land in more than one and the assert fires **regardless of which
draft model is used** — which is exactly what D7 (LFM2 draft) and D10 (dense
SmolLM2-135M) hit on 21/07. Upstream is working on "spec decoding in mamba cache
align mode"; nothing has landed.

## 5. CPU ngram — corrupts output, and it explains submit_015

`tools/runpod/ngram_check.sh`: greedy equivalence **1/6** against a same-session
reference. The mismatches are unmistakable **token duplication**:

```
'green green'   'red\nred'   'blue blue'   'three rows rows'
'def triangular(nNC(n):'   '1313–18'   'A1717'   'vLLBYN'
```

Greedy speculative decoding is lossless by construction, so this is a vLLM
output-path bug (accepted/bonus tokens emitted twice) on this hybrid model — the
same defect family as `ngram_gpu`. **That is why submit_015 was aborted with
"long-context probe failed (0%) — truncation / dual-path likely": the harness was
reading corrupted text.**

**Method lesson, worth more than the result: the needle test is not sufficient.**
It returned 2/5 for both baseline and ngram, yet the ngram answers themselves
carried the corruption (`turquoise9-9`, `4X7-7Q2, M4XFR`) and only passed because
scoring is substring-based. **Gate every future mechanism on exact greedy
equivalence; treat needle as secondary.**

## 6. Fusion passes / custom ops — null to negative

v0.25.1 ships `custom_ops: ['none']`, `rms_norm=['native']`, and `pass_config`
`fuse_norm_quant`/`fuse_act_quant` both False, which looked like free wins
against the ~1.9ms term.

| config | TPOT p50 | TTFT p50 | needle |
|---|---|---|---|
| H0 control (hogged) | **7.80ms** | **317ms** | 2/5 |
| H5 `fuse_norm_quant`+`fuse_act_quant` | 7.98 (+2.3%) | 361 (+14%) | 2/5 |
| H7 H5 + `+rms_norm,+silu_and_mul` | 7.94 (+1.8%) | 372 (+17%) | 2/5 |

Inductor's own fusion already beats the hand-written passes for this model, and
the passes cost real prefill time.

## 7. Incidental: decode CUDA graphs are already FULL by default

Every server log shows:

```
Capturing CUDA graphs (mixed prefill-decode, PIECEWISE): 51/51
Capturing CUDA graphs (decode, FULL): 51/51
```

So `cudagraph_mode=FULL_DECODE_ONLY` can only *remove* the piecewise prefill
graphs, never speed decode up — which retroactively explains submit_014's null
result and H2's (TPOT 3.21 vs H0 3.17, TTFT 131 vs 129 in the un-hogged run).
The cudagraph family is closed with both log evidence and measurement.

## 9. What this session did NOT establish

- The end-to-end bf16/fp8 TPOT ratio on the hogged rig (only GEMM-level, 1.29).
- Whether any vLLM version between v0.22.1 and v0.25.1, or a nightly newer than
  v0.25.1, performs differently. **v0.23.0 and v0.24.0 have never been tested at
  all**, and the one controlled version comparison we own (v0.22.1 fp8 54.11 vs
  v0.25.1 fp8 58.68, same day, same harness) says only that v0.22.1 is worse.
- Whether ngram would accept anything on the real trace. Irrelevant now that it
  corrupts output, but the local replay could never have measured it: prompts are
  synthetic random tokens, so prompt lookup accepts nothing by construction. Any
  past rejection of an input-copying method that rests on `replay_r2.py` alone is
  not evidence.
- Whether the BTC harness changed again between 22/07 and 25/07. The new
  `tokens_per_sec` field on the 25/07 result pages suggests it did; the
  `config_hash` on those pages settles it and has not been checked.
